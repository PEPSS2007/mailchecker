How Verification Works

Our modular 6-stage pipeline guarantees safety, privacy, and RFC adherence.

01

Stage A: Parse & Normalize

Splits inputs on commas, semicolons, and whitespace. Validates RFC 5322 syntax using email-validator and enforces domain casing and deduplication.

02

Stage B: DNS & Mail Routing

Queries DNS MX records with dnspython. Detects RFC 7505 Null MX (which explicitly refuses email) and evaluates RFC 5321 A/AAAA mail fallback.

03

Stage C: Heuristic Profiling

Cross-references a bundled database of disposable/burner domains and detects role accounts (e.g. admin@, support@) without altering core verdicts.

04

Stage D: Safe SMTP Probe

Initiates a restricted handshake (EHLO, MAIL FROM, RCPT TO, QUIT). Never issues DATA command or transmits email body.

05

Stage E: Catch-All Detection

Probes a synthetic randomized recipient on the domain. If the server accepts fake addresses, it is flagged as Catch-All and classified as Unknown.

06

Stage F: Conservative Verdict

Standardizes outcomes into deliverable, bounce, or unknown with actionable reasons and honest degraded mode handling.

Security & Privacy Protocol

Ethical Safeguards & Honest Limitations

🛡️
Zero Message Transmission

SMTP conversations terminate immediately after RCPT TO with a QUIT command. The DATA command is blocked by code assertions.

🔒
No Data Retention & Safe Logging

Submitted emails are processed strictly in-memory and never stored. All application logs mask local parts (e.g. j***e@domain.com).

🌐
SSRF Protection & Concurrency Limits

Resolved MX host IP addresses are checked against private, loopback, and link-local CIDRs before opening sockets. Per-domain semaphores prevent mail-server overload.

⚠️
Deliverability Limitations

A positive SMTP acceptance proves the mailbox exists at check time, but does not guarantee spam-filter placement or future inbox delivery.
